## 2. 共通方針

本書のすべての API に共通して適用する事項。

| No | 事項 | 決定 | 理由 |
| --- | --- | --- | --- |
| 1 | ベースパス | すべての API は `/api` で始まる（例：`/api/inquiries`） | 本番では画面と API を同じ CloudFront のドメインで提供し、EC2 上の nginx が `/api/*` だけを Rails へ転送する（[技術スタック](tech-stack.md) 9.）。画面の URL と API の URL をこの接頭辞で区別する |
| 2 | データ形式 | 要求・応答ともに JSON（`Content-Type: application/json`） | Next.js の `fetch` と Rails の API モードの標準的な組み合わせ |
| 3 | 項目名 | camelCase（例：`customerName`、`listId`、`dueOn`、`displayOrder`） | JavaScript / TypeScript の慣習に合わせる。Rails と DB の snake_case（`customer_name`）との変換は Rails が行う（要求は受け取った直後に snake_case へ、応答は返す項目を明示して camelCase で組み立てる） |
| 4 | 日付 | `YYYY-MM-DD` の文字列（例：`"2026-11-01"`） | ISO 8601 の日付形式。`received_on`・`due_on`（`date` 型）に対応 |
| 5 | 日時 | ISO 8601 の UTC 表記（末尾 `Z`、ミリ秒まで。例：`"2026-10-31T01:00:00.123Z"`） | `created_at`・`updated_at`（UTC で保存。[データ設計書](data-design.md) 5.4）に対応。本バージョンの画面は日時を表示しない |
| 6 | 値が無い項目 | JSON の `null` で返す。項目自体を省略しない | データ設計書 2. 方針 4（未入力は `NULL`）に対応。項目が常に存在する方がフロントエンドの型定義が単純になる |
| 7 | 区分値 | 種別は `question` / `bug` / `request` / `other`、優先度は `high` / `medium` / `low`、リストは `open` / `working` / `closed` を DB の値のまま返す | 表示名への変換はフロントエンドが行う（データ設計書 9.）。画面モック `mock/script.js` と同じ値 |
| 8 | 識別子 | 問い合わせの `id` は数値、リストの `id` は文字列 | データ設計書 4.1・4.2 の型に対応 |
| 9 | 認証 | 行わない | [要件定義書](requirements.md) 決定事項 No.9（ログイン機能は設けない）に従う。アクセス元の制限も行わない（要件定義書 7.「アクセス制御」・決定事項 No.20） |
| 10 | CORS | 開発環境でだけ、送信元 `http://localhost:3000` からの呼び出しを許可する。本番では許可しない | 開発時は画面（3000）と API（3001）のポートが異なるため（[技術スタック](tech-stack.md) 3.）。本番は画面と API が同じドメインのため不要 |
| 11 | 文字列の入力値 | 前後の空白（全角の空白を含む）を取り除いてから検査・保存する。任意項目で取り除いた結果が空なら `null` として保存する | [データ要件書](data-requirements.md) 2.1・2.2、データ設計書 5.1 |

### 2.1 エラー応答の形式

処理に失敗したときは、**Problem Details**（[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details for HTTP APIs）の形式で返す。タスク管理アプリ（Spring の `ProblemDetail`）と同じ形である。Rails には標準の仕組みが無いため、`ApplicationController` の `rescue_from` で例外をこの形式に変換する。

```json
{
  "title": "Not Found",
  "status": 404,
  "detail": "問い合わせが見つかりません: id=999",
  "instance": "/api/inquiries/999"
}
```

| 項目 | 内容 |
| --- | --- |
| `type` | エラー種別を表す URI。本バージョンでは種別を細分化せず、省略する（省略時は `about:blank` とみなされる） |
| `title` | HTTP ステータスの標準的な名称 |
| `status` | HTTP ステータスコード（数値） |
| `detail` | 人が読むための説明。**すべて日本語** で返す。Rails がすべての例外を自分で変換するため、タスク管理アプリのように英語の `detail` が混ざることは無い |
| `instance` | エラーが発生した要求のパス |

応答の `Content-Type` は `application/problem+json` とする。

#### 入力チェックのエラー（422）

登録・更新の要求 body が入力チェックに通らなかったときも同じ形式で返す。項目ごとの誤りは次のように含める。

```json
{
  "title": "Unprocessable Content",
  "status": 422,
  "detail": "件名を入力してください、問い合わせ者を入力してください",
  "instance": "/api/inquiries",
  "errors": [
    { "field": "title", "message": "件名を入力してください" },
    { "field": "customerName", "message": "問い合わせ者を入力してください" }
  ]
}
```

| 項目 | 内容 |
| --- | --- |
| `detail` | 項目ごとのメッセージ（日本語）を「、」でつないだもの。**フロントエンドはこれをそのまま表示すればよい** |
| `errors` | 項目ごとの内訳。`field` は要求 body の項目名（camelCase）、`message` はその項目のメッセージ。RFC 9457 が認める拡張メンバーとして付ける |

メッセージは Rails の validations のエラーを日本語の辞書（`config/locales/ja.yml`）で翻訳して作る。

### 2.2 使用する HTTP ステータス

| コード | 意味 | 本書での用途 |
| --- | --- | --- |
| 200 OK | 成功 | 取得・編集・移動に成功した。編集・移動では本文に更新後の問い合わせを返す |
| 201 Created | 作成に成功 | 登録に成功した。本文に作成した問い合わせを、`Location` ヘッダーにその URL（例：`/api/inquiries/9`）を返す |
| 204 No Content | 成功（本文なし） | 全リストの優先度順並べ替え（11.）または削除（12.）に成功した |
| 400 Bad Request | 要求の形が不正 | 要求 body が JSON として読めない |
| 404 Not Found | 対象が存在しない | パスで指定した `id` の問い合わせが無い（取得・編集・移動・削除とも）。**ほかのメンバーが削除した問い合わせを操作したとき** もこれになる（2.3） |
| 422 Unprocessable Content | 内容が不正 | 要求 body が入力チェックに通らない（2.1）。body で指定した `listId` のリストが存在しない |
| 500 Internal Server Error | サーバー内部の失敗 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

入力チェックのエラーを、タスク管理アプリの 400 ではなく 422 にするのは、Rails の慣例（`render ..., status: :unprocessable_content`）に合わせるためである。「JSON として読めない」（形の誤り）と「読めたが内容が規則に合わない」を区別できる。

パスの `id` が数値でないとき（例：`/api/inquiries/abc`、`/api/inquiries/1abc`）は、該当する問い合わせが無いものとして 404 にする。Rails の `find` は `1abc` を `1` と読むため、数字だけかを先に確かめる。

コントローラーに届く前に起きる失敗も、同じ Problem Details の形式で返す。Rails の `config.exceptions_app` に、この形式で返す処理（`backend/lib/problem_details_exceptions_app.rb`）を設定する。開発環境では Rails の詳しいエラー画面が先に出るため、この形式になるのは本番とテストである。

| 状況 | ステータス | `detail` |
| --- | --- | --- |
| 本書に無い URL・メソッド（例：`/api/unknown`、`PUT /api/inquiries/1`） | 404 | `指定された URL はありません` |
| body に UTF-8 として読めない文字が含まれる | 400 | `要求を読めません` |
| 処理中の想定外の失敗（DB に接続できないなど） | 500 | `サーバーでエラーが発生しました`（原因はログにだけ書き、応答には出さない） |

### 2.3 複数のメンバーが同時に使うときの扱い

[要件定義書](requirements.md) 決定事項 No.17・[データ要件書](data-requirements.md) 5.1 を、API では次のように実現する。

| 状況 | API の振る舞い |
| --- | --- |
| ほかのメンバーの変更を見る | API は変更を通知しない。フロントエンドが画面を開いたとき・書き込みのあとに一覧を取り直したときに、最新の状態が返る |
| 同じ問い合わせを同時に編集した | 後から届いた要求の内容で上書きする（後勝ち）。編集は **変えた項目だけを送る**（9.）ため、別々の項目を変えた場合はどちらの変更も残る。同じ項目を変えた場合だけ、後の値になる |
| ほかのメンバーが削除した問い合わせを操作した | 404 を返す。フロントエンドは「保存できなかった」旨を通知し、一覧を取り直す |
| 同じリストの表示順を同時に変えた | Rails がリストの行をロックし、1 つずつ順番に処理する（[データ設計書](data-design.md) 6.2）。後の要求は前の結果に対して適用される |
| 移動・並べ替えの位置が古い画面に基づいている | 指定された位置（`displayOrder`）が枚数以上なら末尾に置く。結果の並びは書き込みのあとの取り直しで画面に反映される |

## 6. GET `/api/inquiries` — 問い合わせ一覧の取得

アプリを開いたとき（再読み込みを含む）に全件を取得し（FR-09）、書き込みのあとに影響を受けたリストを取り直すときにも使う。

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| クエリ | `listId` | string | 任意 | 指定したリストの問い合わせだけを返す。省略時は全件 |

```
GET /api/inquiries
GET /api/inquiries?listId=open
```

### 応答

| ステータス | 本文 |
| --- | --- |
| 200 | 4.2 の形式の配列。`listId`（リストの並び順：未対応 → 対応中 → 完了）、`displayOrder` の昇順。該当が無ければ空の配列 `[]`。存在しない `listId` を指定したときも空の配列 |
| 500 | DB に接続できないなど |

### ボード全体を 1 回で返す API を用意しない理由

リストと問い合わせを入れ子にした形（リストごとに問い合わせの配列を持つ）で返す API も考えられるが、取得のたびに 2 つの形を組み立てる必要がある。リスト（3 件で固定）と問い合わせを別々に取り、フロントエンドで `listId` ごとに分ける方が、API の形が単純になる。タスク管理アプリと同じ方針である。

## 8. POST `/api/inquiries` — 問い合わせの登録

ボード画面（SC-01）の「未対応」列の下部にある「＋ 問い合わせを登録」から、新しい問い合わせを登録する（[機能要件書](functional-requirements.md) FR-01、[データ要件書](data-requirements.md) 5. の D1）。

### 要求

`Content-Type: application/json` で、次の項目を持つ JSON を body に送る。

| 項目 | 型 | 必須 | 内容 | 入力チェック |
| --- | --- | --- | --- | --- |
| `title` | string | 必須 | 件名 | 前後の空白を除いて 1 文字以上、100 文字以内 |
| `customerName` | string | 必須 | 問い合わせ者 | 前後の空白を除いて 1 文字以上、50 文字以内 |
| `content` | string | 必須 | 問い合わせ内容 | 前後の空白を除いて 1 文字以上、2,000 文字以内 |
| `category` | string | 任意 | `question` / `bug` / `request` / `other`。省略または `null` のときは `question` | 4 つの値のいずれか |
| `priority` | string | 任意 | `high` / `medium` / `low`。省略または `null` のときは `medium` | 3 つの値のいずれか |

```
POST /api/inquiries
Content-Type: application/json

{ "title": "ログインできない", "customerName": "山田 太郎", "content": "パスワードを再設定してもログイン画面に戻される。", "category": "bug", "priority": "high" }
```

- `listId` は **受け取らない**。登録は必ず「未対応」（`open`）に行う（[要件定義書](requirements.md) 決定事項 No.10）。body に含まれていても無視する。
- `contact`・`memo`・`assignee`・`dueOn` は **受け取らない**。登録時点では未設定（`null`）とし、登録後に編集 API（9.）で設定する（FR-01、決定事項 No.13）。body に含まれていても無視する。
- `receivedOn` はサーバーが日本時間の今日の日付を設定する（[データ設計書](data-design.md) 5.4）。body で指定しても無視する。
- `id`・`displayOrder`・`createdAt`・`updatedAt` はサーバーが決める。body で指定しても無視する。

### 処理

1. 各項目の前後の空白（全角の空白を含む）を取り除き、`category`・`priority` が無ければ既定値を補う。
2. 「未対応」リストの `lists` の行を行ロックする（[データ設計書](data-design.md) 6.2）。
3. 受付日に日本時間の今日を入れ、問い合わせを「未対応」リストの **末尾** に追加する。入力チェックに通らなければ 422 を返し、何も保存しない。
4. 「未対応」リストの問い合わせ全件を [機能要件書](functional-requirements.md) 3.1「優先度順の並べ替え規則」に従って並べ直す（14.「並べ替えの実装」）。末尾に追加してから並べ直すため、新しい問い合わせは **優先度も対応期限も同じまとまりの末尾** に入る（登録時は対応期限が無いため、同じ優先度の中の最後になる）。
5. 並べ直した結果を `displayOrder` に 0 からの通し番号として書き込む。`displayOrder` が変わった既存の問い合わせは `updatedAt` も現在時刻に更新する。
6. 2〜5 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

### 応答

| ステータス | 本文 |
| --- | --- |
| 201 | 4.2 の形式のオブジェクト 1 件（登録した問い合わせ）。`Location` ヘッダーに `/api/inquiries/{id}` |
| 400 | body が JSON として読めない |
| 422 | 入力チェックに通らない（2.1「入力チェックのエラー」の形式、`errors` 付き）。必須の 3 項目が空なら、空の項目すべてを `errors` に含める |
| 500 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

### 登録後に画面へ反映する方法

応答で返るのは登録した問い合わせ 1 件だけだが、処理 4〜5 のとおり **「未対応」の他の問い合わせの `displayOrder` も変わりうる**。フロントエンドは応答の 1 件を手元の一覧に差し込むのではなく、成功後に `GET /api/inquiries?listId=open`（6.）で「未対応」を取り直して置き換える。これにより、並べ替えの規則をフロントエンドに持たせずに済む。取り直しによって、ほかのメンバーが「未対応」に加えた変更も画面に反映される。

### 並べ替え後の一覧を応答で返さない理由

「登録後のリスト全件を返す」形にすれば通信は 1 回で済むが、「作成したリソース 1 件を返す」という REST の一般的な形から外れ、他の API と応答の形が揃わなくなる。リスト 1 つ分を取り直す負担は小さいため、応答の形の一貫性を優先する。タスク管理アプリと同じ方針である。

## 9. PATCH `/api/inquiries/{id}` — 問い合わせの編集

問い合わせ詳細（SC-02）で、件名・問い合わせ者・連絡先・種別・問い合わせ内容・対応メモ（FR-02）、対応者（FR-06）、対応期限（FR-07）、優先度（FR-08）を編集する（[データ要件書](data-requirements.md) 5. の D2）。問い合わせ詳細には「保存」ボタンが無く、項目ごとに確定したときにフロントエンドがこの API を呼ぶ（[フロントエンド設計書](frontend-design.md) 8.6）。

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| パス | `id` | number | 必須 | 編集する問い合わせの識別子 |

`Content-Type: application/json` で、**変更する項目だけ** を body に送る。送らなかった項目は変更しない。少なくとも 1 項目を送る。

| 項目 | 型 | `null` を送れるか | 内容 | 入力チェック |
| --- | --- | --- | --- | --- |
| `title` | string | 送れない | 件名 | 前後の空白を除いて 1 文字以上、100 文字以内 |
| `customerName` | string | 送れない | 問い合わせ者 | 前後の空白を除いて 1 文字以上、50 文字以内 |
| `contact` | string / null | 送れる（未入力にする） | 連絡先 | 100 文字以内。形式は検査しない |
| `category` | string | 送れない | 種別 | 4 つの値のいずれか |
| `content` | string | 送れない | 問い合わせ内容 | 前後の空白を除いて 1 文字以上、2,000 文字以内 |
| `memo` | string / null | 送れる（未入力にする） | 対応メモ | 2,000 文字以内 |
| `assignee` | string / null | 送れる（未割当にする） | 対応者 | 50 文字以内 |
| `dueOn` | string（日付）/ null | 送れる（解除する） | 対応期限 | `YYYY-MM-DD` の形式で、実在する日付。過去の日付も可 |
| `priority` | string | 送れない | 優先度 | 3 つの値のいずれか |

```
PATCH /api/inquiries/1
Content-Type: application/json

{ "assignee": "小林" }
```

```
PATCH /api/inquiries/1
Content-Type: application/json

{ "dueOn": null }
```

- 「項目を送らない」（変更しない）と「`null` を送る」（値を消す）を区別する。Rails では body にその項目のキーがあるかどうかで判定する。
- 任意項目（`contact`・`memo`・`assignee`）に空文字や空白だけを送ったときは、`null` を送ったのと同じに扱う（2. 方針 11）。
- `listId`・`displayOrder` は **含めない**。ステータス変更と並べ替えは 10. の API で行う。body に含まれていても無視する。
- `id`・`receivedOn`・`createdAt`・`updatedAt` は変更できない。body で指定しても無視する。
- 変更できる項目が 1 つも無い body（空の `{}` など）は 422 とする。`detail` は `変更する項目を指定してください`、`errors` は空の配列。

### 処理

1. `id` の問い合わせを取得する（無ければ 404）。
2. 送られた項目だけを、前後の空白を取り除いてから問い合わせに書き込む。入力チェックに通らなければ 422 を返し、何も保存しない。
3. **`priority` が送られ、変更前と異なるときだけ**、次を行う。
   1. その問い合わせのリストの `lists` の行を行ロックし、リストの問い合わせを読み直す（[データ設計書](data-design.md) 6.2）。
   2. 変更した問い合わせをリストの末尾に移してから、8.「処理」4〜5 と同じ規則（[機能要件書](functional-requirements.md) 3.1）でリスト内を並べ直し、`displayOrder` を 0 からの通し番号として書き込む。変更した問い合わせは、**変更後の優先度の中で、対応期限に応じた位置**（優先度も対応期限も同じものがあればその末尾）に入る（FR-08）。
4. それ以外の項目の変更（対応期限の変更を含む）では、並びには触らない（[機能要件書](functional-requirements.md) 3.1）。
5. `updatedAt` を現在時刻にする。2〜3 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

### 応答

| ステータス | 本文 |
| --- | --- |
| 200 | 4.2 の形式のオブジェクト 1 件（編集後の問い合わせ。送らなかった項目も現在の値で含む） |
| 400 | body が JSON として読めない |
| 404 | 指定した `id` の問い合わせが存在しない（ほかのメンバーが削除した場合を含む） |
| 422 | 入力チェックに通らない（2.1 の形式、`errors` 付き）。必須項目を空にした、`null` を送れない項目に `null` を送った、`dueOn` が日付として読めない（`detail` は `対応期限は YYYY-MM-DD の形式で指定してください`）、変更できる項目が 1 つも無い |
| 500 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

### 編集後に画面へ反映する方法

優先度を変えたときは、8. と同じく同じリストの他の問い合わせの `displayOrder` も変わりうる。フロントエンドは成功後に `GET /api/inquiries?listId=<その問い合わせのリスト>`（6.）でリストを取り直して置き換える。優先度以外の編集でも同じ手順にし、「編集したら取り直す」の 1 通りにそろえる。

### 変えた項目だけを送る（PATCH）理由

タスク管理アプリでは、編集できる 4 項目をすべて送る `PUT` にした（「`null` で解除」と「送らない」の区別を避けるため）。本システムでは編集できる項目が 9 つに増え、チームの複数のメンバーが同時に使う（[要件定義書](requirements.md) 5.1）。全項目を送る形だと、メンバー A が対応者を変えた直後に、古い画面を開いていたメンバー B が対応メモだけを変えたとき、B の要求に含まれる **古い対応者** で A の変更を書き戻してしまう。これは「操作していない項目を古い値で書き戻さない」（[データ要件書](data-requirements.md) 5.1、要件定義書 7.「同時利用」）に反する。

変えた項目だけを送る `PATCH` にすれば、別々の項目への変更はどちらも残る。「送らない」と「`null` を送る」の区別は、Rails では body のキーの有無で自然に判定できるため、実装の負担も小さい。

## 10. PUT `/api/inquiries/{id}/position` — ステータス変更・並べ替え

問い合わせを別のリストへ移す（ステータス変更。FR-04）、または同じリスト内で並べ替える（FR-05）。どちらも「移動先のリストと、その中での位置」を指定する 1 つの API で扱う（[データ要件書](data-requirements.md) 5. の D1・D2）。次の 2 つの画面操作から呼ばれる。

| 画面操作 | 送る値 |
| --- | --- |
| ボード画面（SC-01）でのドラッグ&ドロップ | 移動先の `listId` と、ドロップした位置の `displayOrder` |
| 問い合わせ詳細（SC-02）でのステータスの選択 | 選んだステータスの `listId` だけ（`displayOrder` は送らない → 移動先の末尾。[要件定義書](requirements.md) 決定事項 No.18） |

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| パス | `id` | number | 必須 | 動かす問い合わせの識別子 |

| 項目 | 型 | 必須 | 内容 | 入力チェック |
| --- | --- | --- | --- | --- |
| `listId` | string | 必須 | 移動先のリストの `id`。同じリスト内の並べ替えでは現在のリストを指定する | `lists` テーブルに存在すること |
| `displayOrder` | number / null | 任意 | 移動先のリストで、**自分を除いた並び** の何番目（0 始まり）に入るか。リストの件数以上、または省略・`null` のときは末尾 | 0 以上の整数 |

```
PUT /api/inquiries/3/position
Content-Type: application/json

{ "listId": "working", "displayOrder": 1 }
```

```
PUT /api/inquiries/3/position
Content-Type: application/json

{ "listId": "closed" }
```

### 処理

1. `id` の問い合わせを取得する（無ければ 404）。
2. `listId` のリストが存在することを確認する（無ければ 422）。
3. 移動元（問い合わせの現在の `listId`）と移動先のリストの `lists` の行を 1 つの SQL でまとめて行ロックし、問い合わせを読み直す（[データ設計書](data-design.md) 6.2）。
4. 移動元のリストの並びからその問い合わせを外す。
5. 移動先のリストの並び（移動元と同じリストなら 4. で外したあとの並び）の `displayOrder` の位置に問い合わせを差し込む。位置が件数以上、または指定が無ければ末尾に置く。別のリストへ動かしたときは問い合わせの `listId` を書き換える。
6. 移動元と移動先のリストそれぞれについて、`displayOrder` を 0 からの通し番号として書き直す（同じリストなら 1 つ）。動かした問い合わせと、位置が変わった問い合わせは `updatedAt` を現在時刻にする。
7. **優先度順の並べ替えは行わない**。指定した位置がそのまま保存される（[機能要件書](functional-requirements.md) 3.1）。
8. 3〜6 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

ステータスの移り方に制限は無い（「完了」から「未対応」へ戻すこともできる。FR-04）。

### 応答

| ステータス | 本文 |
| --- | --- |
| 200 | 4.2 の形式のオブジェクト 1 件（移動後の問い合わせ。`listId` と `displayOrder` が新しい値） |
| 400 | body が JSON として読めない |
| 404 | 指定した `id` の問い合わせが存在しない（ほかのメンバーが削除した場合を含む） |
| 422 | 入力チェックに通らない（2.1 の形式）。`listId` が無い・空（`移動先のリストを指定してください`）、`displayOrder` が 0 以上の整数でない（`表示順は0以上の整数で指定してください`）。`listId` のリストが存在しない（`detail` は `リストが見つかりません: listId=xxx`） |
| 500 | DB に接続できないなど。フロントエンドは元の位置に戻し、「保存されていない」旨を通知する（FR-09） |

### 移動後に画面へ反映する方法

移動元・移動先の両方のリストで `displayOrder` が振り直されるため、フロントエンドは成功後に `GET /api/inquiries?listId=` を移動元と移動先について呼び（同じリストなら 1 回）、取り直して置き換える。ドラッグ&ドロップでは、ドロップした瞬間に問い合わせがその位置に見えている必要があるため、フロントエンドは API を呼ぶ前に手元の並びを先に変える（楽観更新）。詳細は[フロントエンド設計書](frontend-design.md) 5.6。

### 編集 API（9.）に `listId` を含めない理由

編集（問い合わせ詳細の入力）とステータス変更・並べ替えは、扱う規則が違う。ステータス変更だけが 2 つのリストの振り直しを伴う。1 つの API に混ぜると、「優先度も変わりリストも変わった」ときにどちらの規則を適用するかが複雑になる。分けておけば、9. は「優先度が変わったら並べ直す」、10. は「並べ直さない」と規則が 1 つずつで済む。問い合わせ詳細のステータスの選択も、並べ直さない操作なので 10. を使う。

### 位置の指定を「自分を除いた並びの何番目か」とする理由

ドラッグ&ドロップのライブラリ（`@hello-pangea/dnd`）が返す移動先の `index` がこの定義であり、フロントエンドが値を変換せずにそのまま送れる。同じリスト内で下へ動かすときに「自分を数えるかどうか」で 1 つずれる混乱を避けられる。

## 11. POST `/api/inquiries/sort` — 全リストの優先度順並べ替え

ボード画面（SC-01）のツールバーにある「優先度順に並べ替え」で、3 つのリストすべての問い合わせを並べ直す（[機能要件書](functional-requirements.md) FR-10、[データ要件書](data-requirements.md) 5. の D1）。

### 要求

パラメータも body も無い。

```
POST /api/inquiries/sort
```

### 処理

1. 3 つのリストの `lists` の行を、1 つの SQL でまとめて行ロックする（[データ設計書](data-design.md) 6.2）。
2. リストごとに、順に次を行う。
   1. そのリストの問い合わせを `displayOrder` の昇順で取り出す。
   2. [機能要件書](functional-requirements.md) 3.1 の規則で並べ直す：優先度が 高 → 中 → 低、同じ優先度の中は対応期限の近い順（未設定は後ろ）、優先度も対応期限も同じものは今の順序を保つ（14.「並べ替えの実装」）。FR-10 には「操作した問い合わせ」が無いので、末尾に置くものも無い。
   3. `displayOrder` を 0 からの通し番号として書き込む。位置が変わった問い合わせだけ `updatedAt` を現在時刻にする。
3. 3 リスト分を 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

既に並んでいるリストは何も変わらない。何回呼んでも結果は同じ（冪等）。

### 応答

| ステータス | 本文 |
| --- | --- |
| 204 | 本文なし |
| 500 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

### 並べ替え後に画面へ反映する方法

3 つのリストすべての `displayOrder` が変わりうるため、フロントエンドは成功後に `GET /api/inquiries`（6.。`listId` なし）で全件を取り直して置き換える。

### なぜ `POST` で `/sort` なのか、なぜ本文を返さず `204` にするのか

並べ替えは「リソースを作る・置き換える」ではなく「サーバーに処理を頼む」操作であり、対象も 1 件に定まらないため、`POST` で動作を表すパス（`/sort`）にする。返すべきリソースが 1 つに定まらないため、本文の無い `204` にする。タスク管理アプリと同じ方針である。

## 12. DELETE `/api/inquiries/{id}` — 問い合わせの削除

問い合わせ詳細（SC-02）の「問い合わせを削除」で、確認ダイアログの OK を押したあとに、問い合わせを削除する（[機能要件書](functional-requirements.md) FR-03）。確認ダイアログはフロントエンドが表示し、API は確認の仕組みを持たない。

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| パス | `id` | number | 必須 | 削除する問い合わせの識別子 |

```
DELETE /api/inquiries/3
```

### 処理

1. `id` の問い合わせを取得する（無ければ 404）。
2. その問い合わせのリストの `lists` の行を行ロックする（[データ設計書](data-design.md) 6.2）。
3. 問い合わせを削除する（物理削除。[データ設計書](data-design.md) 2. 方針 3）。
4. そのリストの残りの問い合わせの `displayOrder` を 0 からの通し番号として詰め直す。並べ替えの規則による並べ直しは行わない（[機能要件書](functional-requirements.md) 3.1）。
5. 2〜4 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

### 応答

| ステータス | 本文 |
| --- | --- |
| 204 | 本文なし |
| 404 | 指定した `id` の問い合わせが存在しない（既に削除されている場合を含む） |
| 500 | DB に接続できないなど。フロントエンドは「削除されていない」旨を通知する（FR-09） |

### 削除後に画面へ反映する方法

フロントエンドは成功後に `GET /api/inquiries?listId=<削除した問い合わせのリスト>` でリストを取り直す。404 のとき（ほかのメンバーが先に削除していた場合）も、同じリストを取り直して画面から消す。

### 確認や取り消しの仕組みを API に持たない理由

削除の確認は画面の操作の問題であり、確認ダイアログはフロントエンドが出す（FR-03）。API に「確認済み」を表す項目を加えても、フロントエンドがそれを付けて送るだけになり、守りが増えるわけではない。取り消し（アンドゥ）は提供しない（[要件定義書](requirements.md) 8.）ため、削除済みの印を付けて残す仕組みも持たない（個人情報を残さないためでもある。[データ要件書](data-requirements.md) 2.3）。

## 14. 実装上の注意

### 並べ替えの実装

[機能要件書](functional-requirements.md) 3.1 の規則は「優先度も対応期限も同じものは元の順序を保つ」（安定ソート）を前提にしている。Ruby の `sort_by` は **安定ソートではない**（同じ値どうしの順序が保たれる保証が無い）ため、元の並びの位置を最後の比較の材料に加えて、順序を確定させる。

```ruby
# inquiries は displayOrder の昇順（登録・優先度変更では、操作した問い合わせを末尾に移したあと）
PRIORITY_RANK = { "high" => 0, "medium" => 1, "low" => 2 }.freeze

sorted = inquiries.each_with_index.sort_by do |inquiry, index|
  [
    PRIORITY_RANK.fetch(inquiry.priority),
    inquiry.due_on.nil? ? 1 : 0,          # 対応期限が未設定のものは後ろ
    inquiry.due_on || Date.new(0),        # 対応期限の近い順（nil どうしは同じ値として比べる）
    index                                 # 元の位置：同じものどうしの順序を保つ
  ]
end.map(&:first)
```

並べ替えは DB の `ORDER BY` ではなく Rails のコードで行う。「操作した問い合わせを末尾に移してから並べる」という手順を SQL で表すのは複雑になるためである。1 リストは最大でも 300 件程度であり、メモリ上での並べ替えで十分に速い。
